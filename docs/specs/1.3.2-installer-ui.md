# Спека: установщик 1.3.2 — прогресс, брендинг TUI, процентные размеры

Три связанные доработки установщика (план от 2026-11-17). Затрагивают:
экран установки, все диалоги мастера, расчёт размеров LV.

## 1. Прогресс установки (псевдографика, статусы, остаток времени)

### Корень

Экран 6 показывал консольный вывод этапов (`sgdisk`, `lvcreate`, tar и
т.д.): пользователь видел технический лог без понимания, сколько ещё
ждать. Полевой сценарий: установка на железе 10+ минут, обратная связь
отсутствует.

### Решение (as-built)

Что · значение · где · как проверяется:

- Gauge-диалог · `dialog --gauge` 12×74, фирменная тема, backtitle ·
  `installer/lib/progress.sh` (`progress_begin/stage/end`) · скриншоты
  интерактивного прохода: процент и статус обновляются.
- Этапы · фиксированная шкала 3–100 %: контрольные суммы 3, разметка 8,
  хранилище 13, развёртывание системы 13→60, конфигурация 65, сеть 68,
  WireGuard 70, MikoPBX 72, импорт образа 72→85, загрузчик 95, финал 98 ·
  `installer/vlanit-installer` (экран 6) · шкала в одном месте, веса из
  фактических прогонов стенда.
- Суб-прогресс долгих этапов · `du -sb` целевого каталога каждые 2 с,
  процент = заполнение / распакованный размер ·
  `stage_with_size_progress` (progress.sh) · во время развёртывания
  процент растёт плавно, а не скачком.
- Знаменатель суб-прогресса · байты распакованных `golden.tar.zst` и
  `mikopbx-*.tar.zst` (`zstd -dc | wc -c`), ключи
  `payload.golden_uncompressed` / `mikopbx_uncompressed` ·
  `scripts/40-staging.sh` + `config/release-manifest.yaml` · в собранном
  ISO манифест содержит числа; установщик при null (ISO < 1.3.2)
  отключает суб-прогресс и идёт скачком.
- Оценка остатка · «осталось ~N мин», линейная: прошедшее × (100−pct)/pct ·
  `progress_stage` · видна в тексте gauge после 3 %.
- Ошибка этапа · gauge закрывается (`progress_abort`), `die` показывает
  msgbox с журналом · `common.sh` (die вызывает progress_abort) ·
  искусственный сбой этапа на стенде: msgbox вместо зависшего gauge.
- Autoinstall · gauge не открывается, вывод этапов в консоль/serial как
  раньше (агент парсит serial) · `run_stage` ветка AUTOMODE · сценарии
  regress-full в QEMU проходят без изменений ожиданий.
- Вывод `log()` при открытом gauge · только в журнал и serial, не на
  tty0 (иначе мусор поверх псевдографики) · `common.sh` · визуально в
  прогоне: экран gauge чистый.

### Отклонённые альтернативы

- `pv`/`tar --checkpoint` для прогресса распаковки — лишняя зависимость
  в live-образе; du по готовому каталогу даёт тот же эффект без
  инструментов (ponytail: стандартные средства).
- Отдельный фоновый тикер времени — усложнение: оценка обновляется на
  каждом вызове progress_stage, а долгие этапы тикают каждые 2 с.
- Прогресс по времени (фиктивное заполнение) — врёт при изменении
  скорости носителя; du — факт.

## 2. Брендинг псевдографики

### Корень

Диалоги мастера рисовались цветами dialog по умолчанию (синий фон,
красные теги) — визуально чужеродно для бренда, у которого GRUB, Plymouth
и консоль уже в фирменной палитре (#09090b / #F5F4F0 / #D4AA6A).

### Решение (as-built)

- Тема · `installer/dialogrc` (DIALOGRC): чёрный фон, белый текст,
  жёлтое выделение — 16-цветная аппроксимация палитры бренда; одна тема
  на все диалоги процесса (меню, msgbox, gauge, ошибки) · применяется в
  `common.sh` через `export DIALOGRC` · скриншоты всех экранов мастера.
- Backtitle · «VLANit PBX OS <версия> — установка», версия из
  release-manifest (единый источник) · обёртка `dialog()` в common.sh
  подставляет `--backtitle` каждому вызову · backtitle виден на всех
  экранах.

### Отклонённые альтернативы

- Правка каждого из ~20 вызовов dialog — дублирование backtitle
  (ponytail #26-правило: общий модуль при втором появлении).
- whiptail/newt — смена тулкита не нужна: dialog поддерживает DIALOGRC.
- 256-цветные темы — в консоли установщика (vt) гарантированы только
  базовые 16; на них и сведены.

## 3. Размеры разделов в процентах от диска

### Корень

Root-LV был фиксирован: `installer.system_size_mib: 40960` (40 ГиБ).
На дисках сильно больше или меньше 160 ГиБ это даёт несбалансированное
соотношение System/Data (на 32 ГиБ — установка отказывала; на 1 ТиБ —
Data получала всё, и root-LV всё равно 40 ГиБ).

### Решение (as-built)

- Ключ · `installer.system_size_pct: 25` — root-LV = 25 % usable-диска
  (usable = диск − ESP 1024 МиБ − запас метаданных 128 МиБ); Data —
  остаток · `config/build.yaml` · unit-тесты `tests/unit/test-disk-lib.sh`.
- Функции · `usable_mib`, `installer_root_mib` (pct, округление вниз,
  кламп 1–90), `lv_data_mib` (usable − root) · `installer/lib/common.sh`,
  `disk.sh` · unit-тесты (9 проверок, включая переопределение pct).
- Потребители · расчёт LV (create_storage), минимальный размер диска
  (autoinstall: Data ≥ 8 ГиБ, иначе отказ до деструктивных операций) ·
  `deploy.sh`, `vlanit-installer` · регрессия mirror в QEMU (малый
  профиль 13 ГиБ → root ≈ 3 ГиБ при pct 25).
- Переопределение · autoinstall.yaml: `system_size_pct` (стенд mirror
  использует для малого профиля) · `common.sh` · unit-тест override.
- Минимум Data · константа `DATA_MIN_GIB=8` (common.sh), раньше была
  магическое число в формуле минимума диска · сообщение об ошибке
  называет все три слагаемых.

### Отклонённые альтернативы

- Оставить MiB с умолчанием + pct-опцией — два ключа-источника одного
  значения (конфиг должен иметь потребителя, ponytail #21).
- Процент от полного диска (без вычета ESP/запаса) — на мелких дисках
  root LV не влезал бы в PV: вычитаемое должно быть вычтено до процента.
