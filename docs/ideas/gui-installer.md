# Идея #12: графический HTML-установщик с fallback на TUI

Статус: ПЛАН (запрос Максима, 2026-11-18). До реализации — обсудить
архитектуру на железе флота.

## Запрос

Заменить TUI-мастер (dialog) на графический интерфейс с HTML-разметкой:
картинки на страницах, отдельная страница на каждый этап установки.
Аппаратная поддержка отображения — обязательное требование; TUI
остаётся fallback, если графический интерфейс поднять не удалось.

## Почему это реалистично на нашем железе

- Все целевые устройства — UEFI x86-64. Ядро Debian даёт фреймбуфер
  всегда: `efifb`/`vesafb` есть на любой машине, которая вообще
  загрузила установщик. X/Wayland и видеодрайверы НЕ нужны — вывод
  идёт прямо в `/dev/fb0`.
- Значит «аппаратная поддержка» = проверка наличия `/dev/fb0` +
  рабочего видеорежима (в TUI сейчас этим заведует `all_video` в GRUB,
  графика вешает тот же GOP/VESA путь).
- Python3 уже есть в live-окружении (установщик на нём читает YAML) —
  бэкенд-HTTP поднимается без новых зависимостей.

## Архитектура (предварительная)

```
vlanit-installer (backend, bash — текущая логика без переписывания)
        │  шаги как команды/события
        ▼
локальный HTTP (python3, 127.0.0.1, без внешней сети)
        │  GET  /stage/<n>      — HTML-страница этапа
        │  POST /stage/<n>      — ответ пользователя → backend
        │  GET  /progress       — SSE/поллинг для gauge-прогресса
        ▼
FB-браузер в kiosk-режиме          fallback: dialog TUI (нынешний)
(netsurf-fb или dillo-fb)          при отсутствии /dev/fb0/бинарника
```

- Логика установки (диски, LVM, развёртывание, прогресс) — один
  бэкенд; TUI и GUI — два фронтенда к нему. Autoinstall (YAML) ходит
  в тот же бэкенд мимо обоих фронтендов — регрессии стенда не ломаются.
- Страницы — статический HTML + PNG из branding/ (логотип, иллюстрации
  этапов), без JS-фреймворков (offline, минимализм, ponytail).
- Ввод: FB-браузеры дают формы/кнопки; клавиатура — как сейчас.
  Мышь — бонус, если устройство есть (не требуется).

## Ограничения и риски

- **Размер ISO**: netsurf-fb/dillo + зависимости ≈ +20–60 МБ
  (уточнить по пакетам trixie). Acceptable для офлайн-образа на USB.
- **RAM**: FB-браузер + рендер PNG — десятки МБ; минимум ОЗУ
  установщика 2 ГБ — запас достаточен.
- **Проверяемость**: скриншоты через monitor-screendump работают и с
  графикой (пиксели), стенд QEMU покрывает без изменений; добавить
  проверку fallback-пути (загрузка с `vga=...` без fb? или
  отключённым фреймбуфером ядра).
- **Live-init**: сейчас `/init` у live — busybox `vlanit-init`; запуск
  plymouthd там уже отсутствует архитектурно (спека
  1.3.2-plymouth-verify). Запуск браузера после switch_root в
  systemd-юните установщика — туда же, где сейчас запускается dialog.

## План внедрения (шаги)

1. **Спайк (0.5–1 день)**: live-rootfs с `netsurf-fb`/`dillo-fb`,
   запуск на `/dev/fb0` в QEMU и на железе флота (минимум 2 модели),
   скриншот-факт. Проверить кириллицу в формах.
2. **Бэкенд-API**: обернуть шаги мастера в команды; прогресс —
   события (уже есть лог-структура stage/percent).
3. **HTML-страницы этапов**: экран 1..7 + gauge (тот же branding,
   плюс иллюстрации: схема разметки дисков, схема зеркала).
4. **Fallback**: `ExecStartPre`-проба fb0+бинарника → при провале
   стартует нынешний dialog-мастер. Автотест обоих путей в QEMU.
5. **Autoinstall и регрессия**: parity сценариев стенда, обновление
   спеки установщика.

## Отклонённые альтернативы (предварительно)

- **Полноценный X/Wayland + Chromium/Firefox**: +400–600 МБ ISO и
  сотни МБ RAM ради установщика — непропорционально (ponytail).
- **GTK/Qt-приложение вместо HTML**: привязка к тулкиту, нельзя
  «менять странички» без пересборки, картинки сложнее. HTML решает
  запрос напрямую.
- **Оставить TUI навсегда**: запрос брендинга и наглядности (схемы
  дисков, картинки) на TUI не закрыть.
